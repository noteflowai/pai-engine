# ADR 0001 · 制品库与流程编排

状态：已采用（2026-10-08）。任务 `pai-artifact-platform-20261008`，逻辑角色 `pai-workbench`。

## 背景

用户给出的交付形态："PAI平台交付的制品形态：1，制品库（算法和模型）；2，通用制品的编排平台（可以配置业务流程）。PAI平台做80–90%，以后基本是按Token结算，交付的是制品。比如：交付场外物流的规划算法。"

据此 PAI 交付的不是一次对话，而是**可独立核验的制品**：版本不可变，经自身基准验收，签名打包，能在另一个环境复现；业务流程用配置组合这些制品，不写代码。

## 决策

1. **制品契约 `pai-artifact-1`**（`src/artifacts/contract.ts`）。一个版本 `name@x.y.z` 对应一份清单：类型（`algorithm` / `model`）、带输入输出数据 schema 的操作、能力与限制、运行时与锁文件、每个依赖的版本/许可证/来源、代码出处（源提交）、随附文件的摘要、适用范围、`physicalValidation: false`。去掉构建时间和构建者后的内容摘要就是版本身份：同一版本换内容会被拒绝（`ARTIFACT_IMMUTABLE`），只能发新版本。
2. **插件式适配器**（`ArtifactAdapter`，`src/artifacts/registry.ts` 的 `ADAPTERS`）。增加一类算法或模型只需登记一个适配器（构建、参数、数据校验、运行、验收基准、运行时核对）；注册表和流程引擎不会按制品名分支。
3. **生命周期** `draft → validated → released → deprecated`。`validated` 只能由适配器自己的验收基准（原生运行 + 独立核验器）给出；`released` 和 `deprecated` 只能由人做，且要写理由。流程只能引用 validated / released 的精确版本，已弃用的版本不能再被新流程引用。
4. **签名制品包 `pai-artifact-package-1`**。沿用发布包的签名器（托管 KMS ECDSA P-256，本机 Ed25519）和"规范化清单 → 摘要 → 签名"的方式；可离线核验，可固定信任的公钥。导入时签名者必须可信：本部署自己的密钥，或操作者为这次导入固定的公钥（另行获得），否则 `UNTRUSTED_SIGNER`。**不加载远程代码，也不接受外来声明**：包内代码必须与本版本适配器的可信源逐字节一致（`UNTRUSTED_CODE`），清单里的操作、副作用、schema、上限、依赖固定版本和适用范围也必须与本地构建一致（`UNTRUSTED_CLAIMS`）；导入后仍是草稿，要在本环境重新验收。
5. **流程 `pai-workflow-1`**（`src/artifacts/workflows.ts`）。用校验过的 JSON 描述，三种节点：制品操作、条件（按节点状态放行，否则拒绝或转人工）、人工确认。运行前检查：未知字段、重复 id、引用未解析、数据 schema 不匹配、未知操作或参数、环。运行开始时固定每个制品版本的摘要，节点执行前再核对；按依赖顺序执行，每个节点保存产物摘要、状态、回执和用量；意外错误让运行以 `failed` 结束并写明原因，不会停在"运行中"；**不自动重试**；重启后只恢复声明为无外部副作用的节点；一个 `requestId` 对应一个运行。
6. **用量 `pai-usage-1`**：原生计算（墙钟 s、CPU s、峰值内存、存储字节）和模型 Token 分开记录；没有模型调用记 `none`，量不出来记 `unknown`，不估算、不编造。`priceVersion` 为空：**计费和收费没有上线**。
7. **职责边界**。PAI 负责领域产品、制品契约与适配器、核验器和界面；调度、故障转移、账本和长任务归 noteflow-auto；Agent 网关归 AgentForge。PAI 里不做通用控制器、账本或 ACP 引擎。流程引擎只做"按依赖执行制品节点并留证据"这一件事。

## 第一个制品：场外物流规划 `logistics-pdptw`

- **范围**：公路运输的取送货车辆路径（PDPTW）。约束包括车辆载重、同一辆车先取后送、取货与送货时间窗（含服务和等待时间）、车辆班次、道路距离/时间矩阵，目标是里程成本加每辆车的固定成本。不做厂内 AGV、不做车辆控制、不真实派车。
- **求解器**：Google OR-Tools 路由求解器（PyPI 当前版本，Apache-2.0，2026-01 发布），由 `native/logistics-requirements.txt` 按哈希锁定，只装 wheel。选它的理由：容量、取送配对和时间窗都是现成的维度和约束，开源许可宽松，有确定性首解策略可复现，也有限时局部搜索；规模（≤ 500 单、≤ 100 车、≤ 120 s）在单机 CPU 预算内。不选商业 MIP 求解器（许可和成本），不选 VROOM（同样支持带时间窗的取送货，速度快，但以 C++ 程序或服务交付，没有可按哈希锁定的 Python wheel；OR-Tools 还能用带罚值的析取表达"允许部分不分配"），也不自己写启发式（只作对照基线）。
- **独立核验器** `native/logistics_verify.py`：只用 Python 标准库，与求解器不共享代码，从实例矩阵重新计算路线连续（每辆车至多一条路线）、每单恰好一次、先取后送、载重、时间窗与班次、上报的到达/离开/载重以及总里程、总成本和用车数（必填）、状态一致。计划只有通过核验才可用。
- **状态如实**：`feasible`、`partial`（允许不分配时）、`infeasible`（求解器证明无解，或订单比所有车都重）、`timeout`、`unknown`（没找到解也没有证明）、`error`；`optimality: "not proven"`；确定性策略只有在搜索停在局部最优（不是时间上限）时才标 `replayable: true`。每辆车按自己的单价和固定成本计入目标。
- **基准**：种子固定、合成且标注的实例（`logistics_generate.py`，大圆距离 × 1.3、50 km/h，不是真实路网），并与顺序启发式基线对照。实测结果见 [VERIFICATION.md](../VERIFICATION.md#制品平台)。这些结果只说明行为和正确性，不代表生产收益。

## 第二个制品：场地准入与排队调度 `yard-admission`（2026-10-11）

- **问题**：场地空间有限，车辆按到达时间窗陆续到来。要决定哪些车入场、何时入场、停在堆场哪段时间、上哪个月台、由几组作业班组处理、何时离场；放不下的车本时段不安排，并明确列出。约束：门岗车道与过闸时间、堆场车位按车长占用（场地空间）、月台的货型与车长匹配、作业班组数、作业时长、离场时间与最晚离场；目标按字典序：先最大化按优先级加权的入场车辆，再最小化加权等待加场内停留。
- **算法**：OR-Tools **CP-SAT**（约束规划）。这类带资源约束的调度问题是它的典型场景：可选区间、NoOverlap（月台）、Cumulative（门岗、堆场、班组）都是原生约束。与物流规划共用同一份按哈希锁定的 OR-Tools，不新增依赖。单线程、固定种子、以确定性时间作预算，所以同一输入每次给出同一方案；是否**证明最优**如实报告。
- **对照**：先到先服务（FCFS），即许多场地现在的做法。**独立核验器** `yard_verify.py` 只用标准库，按分钟重算时间窗、匹配、作业时长、过闸顺序、离场、月台不重叠、门岗/堆场/班组容量和汇总数。
- **基准**（种子 7，合成场地：6 个月台、2 条门岗车道、10 个堆场车位、3 组班组）：常规班次 24 车，CP-SAT 入场 23 车、优先级分 37，FCFS 14 车、20 分；高峰 40 车 90 分钟内到达，CP-SAT 15 车、34 分，FCFS 11 车、17 分。两种方案都通过独立核验；方案可复现；篡改的方案被拒绝；没有月台能接的危险品车被列为不安排，而不是被硬塞进去。这些是合成实例上的行为与正确性，不代表生产收益；大实例在预算内只给出最好解，未证明最优。

## 备选方案

| 方向 | 方案 | 结论 |
|---|---|---|
| 制品分发 | OCI 镜像仓库 + ORAS（任意制品推入 OCI registry，cosign / Notation 签名） | 适合多仓分发和镜像生态。当前只有一个部署，制品是几十 KB 的代码和清单；现有签名包已具备摘要、签名、离线核验和 KMS。**暂不引入**；包格式保持自描述，需要跨组织分发时可把同一份包作为 OCI artifact 推送（媒体类型 `application/vnd.pai.artifact-package.v1+json`），签名不变 |
| 模型注册 | MLflow Model Registry、Hugging Face Hub | 擅长模型版本、别名和阶段。缺少本项目要的东西：可执行的验收基准、独立核验器、"精确版本 + 不可变内容"的强约束，以及与发布准入相同的签名。**不引入**；`kind: "model"` 已在契约里，第一个模型制品出现时再评估是否把权重存到这类仓库，清单只记摘要 |
| 调度算法 | 自写启发式、MIP（CBC/HiGHS）、专用调度库 | 启发式只作 FCFS 基线；时间索引 MIP 模型规模随时间粒度暴涨；CP-SAT 对区间与累积资源约束有原生支持，且已按哈希锁定，**选 CP-SAT** |
| 流程引擎 | Temporal、Argo Workflows、Airflow、Step Functions | 擅长长时间、分布式、可重试的任务，但会带来第二个控制面，而且默认重试与"不确定的运行不重放"冲突。长任务、调度和故障转移本就归 noteflow-auto。**不引入**；PAI 只保留类型化 JSON 流程（与现有类型化计划同一思路），需要长任务时把节点交给 noteflow-auto 执行 |
| 签名 | Sigstore cosign、in-toto | 适合公开供应链。现有的 KMS 签名、RFC 3161 时间戳和封存流程已经在用，**保持一致**，不再并存第二套信任根 |

## "PAI 做 80–90%" 的口径

这是目标，不是已达成的说法。口径定义：一个业务交付里，PAI 平台提供的部分（制品契约、注册表、验收与签名、流程编排、运行与证据、界面）占全部交付工作的比例；剩下的是客户自己的数据接入、真实路网或业务规则，以及现场确认。目前只有一个制品，样本不够计算这个比例；以后按每个交付分别记录平台复用部分和定制部分的工作量与代码量，再统计。

## 后果

- 新增一类算法或模型 = 一个适配器 + 一份锁文件 + 一个验收基准，不改注册表和流程引擎。
- 每次运行都有逐节点的证据和用量，以后可以按 Token 或原生计算结算；价格版本和结算没有上线。
- 当前是单租户部署，所有记录带 `tenant` 字段（`workspace`），为以后的租户隔离留好位置；多租户鉴权还没有实现。
